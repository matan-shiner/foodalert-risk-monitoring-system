# Weekly Coverage Audit — 2026-09-26 — RUN FAILED (network egress blocked)

## What happened

This week's scheduled audit could not be performed. Both secondary sources
required by this audit are blocked by this session's network egress policy:

- `https://efoodalert.com/feed/` — `WebFetch` returned `EGRESS_BLOCKED`:
  "Access to efoodalert.com is blocked by the network egress proxy."
- `https://www.foodsafetynews.com/feed/` — `WebFetch` returned `EGRESS_BLOCKED`:
  "Access to www.foodsafetynews.com is blocked by the network egress proxy."

No workaround was attempted (no alternate mirrors, caches, or third-party
fetchers were used), consistent with this environment's own guidance that an
egress denial means the destination is not allowed for this session and
should be reported rather than routed around.

**This is the third consecutive weekly failure for the same reason.** The
2026-09-12 and 2026-09-19 runs both hit the identical `EGRESS_BLOCKED` /
`connect_rejected` policy denial on both hosts. Three weeks running of the
exact same denial on the exact same two hosts confirms this is a standing
environment network-policy gap, not a transient blip: `efoodalert.com` and
`www.foodsafetynews.com` are not on this environment's allowed-domains list.

## How to fix it

An administrator (or the environment owner) needs to open this cloud
environment's settings — the environment menu in the session's title bar,
then **Edit** — and either broaden the network access level or add
`efoodalert.com` and `www.foodsafetynews.com` to the allowed domains. See
https://code.claude.com/docs/en/claude-code-on-the-web for the access-level
options. Once that change is made, this audit will succeed on its next
scheduled run (or can be re-run manually).
