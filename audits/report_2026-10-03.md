# Weekly Coverage Audit — 2026-10-03 — RUN FAILED (network egress blocked)

## What happened

This week's scheduled audit could not be performed. Both secondary sources
required by this audit are blocked by this session's network egress policy:

- `https://efoodalert.com/feed/` — `WebFetch` returned `EGRESS_BLOCKED`:
  "Access to efoodalert.com is blocked by the network egress proxy."
- `https://www.foodsafetynews.com/feed/` — `WebFetch` returned `EGRESS_BLOCKED`:
  "Access to www.foodsafetynews.com is blocked by the network egress proxy."

A direct `curl` through the environment's egress proxy was also attempted as a
sanity check (not as a workaround to bypass the policy) and confirmed the
same denial at the proxy level: `CONNECT tunnel failed, response 403` /
`connect_rejected (organization policy)` for both hosts. No other workaround
(mirrors, caches, third-party fetchers) was attempted, consistent with this
environment's guidance that an egress denial means the destination is not
allowed for this session and should be reported, not routed around.

**This is now the fourth consecutive weekly failure for the same reason.**
The 2026-09-12, 2026-09-19, and 2026-09-26 runs all hit the identical
`EGRESS_BLOCKED` / `connect_rejected` policy denial on both of the same two
hosts. Four weeks running of the exact same denial confirms this is a
standing environment network-policy gap, not a transient blip:
`efoodalert.com` and `www.foodsafetynews.com` are not on this environment's
allowed-domains list, and nothing about that has changed since the issue was
first reported three weeks ago.

## How to fix it

An administrator (or the environment owner) needs to open this cloud
environment's settings — the environment menu in the session's title bar,
then **Edit** — and either broaden the network access level or add
`efoodalert.com` and `www.foodsafetynews.com` to the allowed domains under a
Custom network access level. See
https://code.claude.com/docs/en/cloud-environments#network-access for the
exact steps. Once that change is made, this audit will succeed on its next
scheduled run (or can be re-run manually).
