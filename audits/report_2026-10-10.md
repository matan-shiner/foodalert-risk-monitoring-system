# Weekly Coverage Audit — 2026-10-10 — RUN FAILED (network egress blocked)

## What happened

This week's scheduled audit could not be performed. Both secondary sources
required by this audit are blocked by this session's network egress policy:

- `https://efoodalert.com/feed/` — `WebFetch` returned `ENOTFOUND` (DNS does
  not resolve from this session), and a direct `curl` through the
  environment's egress proxy confirmed the real cause: `CONNECT tunnel
  failed, response 403` — `request blocked: no rule or allowlist entry allows
  host "efoodalert.com"`.
- `https://www.foodsafetynews.com/feed/` — same `CONNECT tunnel failed,
  response 403` denial at the proxy level.

The proxy's own diagnostic (`curl -sS "$HTTPS_PROXY/__agentproxy/status"`)
confirms the proxy itself is up and reachable; it is the organization's
network policy that excludes both hosts, not a transient proxy outage. No
workaround (mirrors, caches, third-party fetchers) was attempted, consistent
with this environment's guidance that an egress denial means the destination
is not allowed for this session and should be reported, not routed around.

**This is now the fifth consecutive weekly failure for the same reason.**
The 2026-09-12, 2026-09-19, 2026-09-26, and 2026-10-03 runs all hit the
identical `connect_rejected` / "no rule or allowlist entry allows host"
policy denial on both of the same two hosts. Five weeks running of the exact
same denial confirms this is a standing environment network-policy gap, not
a transient blip: `efoodalert.com` and `www.foodsafetynews.com` are still not
on this environment's allowed-domains list, and nothing about that has
changed since the issue was first reported four weeks ago.

## How to fix it

An administrator (or the environment owner) needs to open this cloud
environment's settings — the environment menu in the session's title bar,
then **Edit** — and either broaden the network access level, or (at the
**Limited** access level) add `efoodalert.com` and `www.foodsafetynews.com`
under **Allowed domains** (leaving the "Allow package managers" box ticked).
See https://code.claude.com/docs/en/cloud-environments#network-access for
the exact steps. Once that change is made, this audit will succeed on its
next scheduled run (or can be re-run manually).

  gap period (now spanning 31+ days / five missed weekly checks' worth of
