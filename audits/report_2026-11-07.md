# Weekly Coverage Audit — 2026-11-07 — RUN FAILED (network egress blocked)

## What happened

This week's scheduled audit could not be performed. Both secondary sources
required by this audit are still blocked by this session's network egress
policy:

- `https://efoodalert.com/feed/` — a direct `curl` through the environment's
  egress proxy returned `CONNECT tunnel failed, response 403`; the proxy's
  own status endpoint (`curl -sS "$HTTPS_PROXY/__agentproxy/status"`) logs
  this as `connect_rejected` / "gateway answered 403 to CONNECT (policy
  denial or upstream failure)" for host `efoodalert.com:443`.
- `https://www.foodsafetynews.com/feed/` — identical `connect_rejected` / 403
  denial for host `www.foodsafetynews.com:443`.
- `WebFetch` on `https://efoodalert.com/feed/` failed with `ENOTFOUND`,
  confirming the host does not resolve from this session at all (outside
  the session's allowed network domains).

The proxy itself is up and reachable (`"enabled": true`); this is the
organization's network policy excluding both hosts, not a transient proxy
outage.

This run also actively attempted to self-resolve the gap rather than just
report it: it called this environment's `update_environment` tool to
propose adding `efoodalert.com` and `www.foodsafetynews.com` to the
environment's allowed-hosts list. The call was refused by the harness with:
*"nobody is present on this routine run... Don't retry it."* Environment
network changes require a human to approve an interactive prompt, which
does not exist on an unattended scheduled run. No further workaround was
attempted, consistent with this environment's guidance that an egress
denial means the destination should be reported, not routed around.

**This is now the ninth consecutive weekly failure for the same reason.**
The 2026-09-12, 2026-09-19, 2026-09-26, 2026-10-03, 2026-10-10, 2026-10-17,
2026-10-24, and 2026-10-31 runs all hit the identical `connect_rejected`
denial on both of the same two hosts. Nine weeks running of the exact same
denial confirms this is a standing environment network-policy gap that has
not been addressed since it was first reported almost two months ago
(2026-09-12).

## How to fix it

A human needs to approve the network change — this cannot be done from an
unattended scheduled run. Either:

1. **Fire this routine with "Run now"** and approve the `update_environment`
   request when it is prompted during that interactive run (this session
   already has the exact call staged: add `efoodalert.com` and
   `www.foodsafetynews.com` to the Default environment's allowed hosts), or
2. **Make the change directly** in the cloud environment's settings — the
   environment menu in the session's title bar, then **Edit** — and either
   broaden the network access level, or (at the **Limited** access level)
   add `efoodalert.com` and `www.foodsafetynews.com` under **Allowed
   domains** (leaving "Allow package managers" ticked). See
   https://code.claude.com/docs/en/cloud-environments#network-access for
   the exact steps.

Once either change is made, this audit will succeed on its next scheduled
run (or can be re-run manually).
