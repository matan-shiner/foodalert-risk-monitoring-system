# Weekly Coverage Audit — 2026-11-21 — RUN FAILED (network egress blocked)

## What happened

This week's scheduled audit could not be performed. Both secondary sources
required by this audit are still blocked by this session's network egress
policy:

- `https://efoodalert.com/feed/` — `curl` through the environment's egress
  proxy returned `CONNECT tunnel failed, response 403`; the proxy logs this
  as `connect_rejected` for host `efoodalert.com:443`.
- `https://www.foodsafetynews.com/feed/` — identical `connect_rejected` /
  403 denial for host `www.foodsafetynews.com:443`.
- `get_environment` confirms the root cause directly: this session's
  environment (`Default`, personal, `is_default: true`) has `network.type`
  `"limited"` with `allowed_hosts: []` — neither host has ever been added
  to the allowlist.

This is not a transient outage; it is the same standing network-policy gap
reported every week since 2026-09-12.

**This is now the eleventh consecutive weekly failure for the same
reason.** The 2026-09-12, 2026-09-19, 2026-09-26, 2026-10-03, 2026-10-10,
2026-10-17, 2026-10-24, 2026-10-31, 2026-11-07, and 2026-11-14 runs all hit
the identical `connect_rejected` denial on both of the same two hosts.
Eleven weeks running of the exact same denial confirms this is a standing
environment network-policy gap, unaddressed for over two and a half months
since it was first reported.

Per the established pattern for this audit, no attempt was made to call
`update_environment` from this unattended run: that tool requires a human
to approve an interactive prompt, which cannot happen on a scheduled run
with nobody present. Routing around the policy denial is also out of
scope for this task.

## How to fix it

A human needs to approve a network change — this cannot be done from an
unattended scheduled run. Either:

1. **Fire this routine with "Run now"** in an interactive session and
   approve an `update_environment` request adding `efoodalert.com` and
   `www.foodsafetynews.com` to the Default environment's allowed hosts, or
2. **Make the change directly** in the cloud environment's settings — the
   environment menu in the session's title bar, then **Edit** — and either
   broaden network access, or (at **Limited** access) add
   `efoodalert.com` and `www.foodsafetynews.com` under **Allowed domains**
   (leaving "Allow package managers" ticked).

Once either change is made, this audit will succeed on its next scheduled
run (or can be re-run manually).
